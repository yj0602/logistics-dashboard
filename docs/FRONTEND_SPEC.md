# Frontend Specification

## 1. 문서 목적

이 문서는 물류 차량 관제 및 ETA 기반 운영 지원 웹 서비스의 프론트엔드 화면 구조와 동작 규칙을 정의한다.

프론트엔드는 다음 정보를 사용자가 빠르게 파악할 수 있도록 설계한다.

* 현재 차량 운영 상태
* 차량별 현재 위치
* 차량별 예상 도착 시간(ETA)
* 지연 차량 및 지연 시간
* Hub별 차량 도착 현황
* 막차 예상 도착 시간
* 남은 대기 시간
* 중간 배송 투입 가능 여부

본 문서는 화면 구현 기준을 정의한다.

API 요청 및 응답 형식은 `API_CONTRACT.md`를 따른다.

페이지 목록과 라우팅 구조는 `PAGES.md`를 따른다.

---

# 2. 사용자 역할

서비스는 다음 두 가지 사용자 역할을 사용한다.

## 2.1 관리자

관리자는 전체 물류 운영 상태를 확인한다.

조회 범위:

* 전체 Hub
* 전체 차량
* 전체 차량의 현재 위치
* 전체 차량의 ETA
* 전체 지연 차량
* Hub별 운영 상태
* 직원별 중간 배송 투입 가능 여부

관리자는 특정 Hub에 제한되지 않는다.

---

## 2.2 현장 직원

현장 직원은 자신이 소속된 Hub와 관련된 정보만 확인한다.

조회 범위:

* 자신의 소속 Hub
* 자신의 Hub로 이동 중인 차량
* 해당 차량의 현재 위치
* 해당 차량의 ETA
* 막차 ETA
* 자신의 중간 배송 투입 가능 여부

현장 직원 화면에는 다른 Hub의 상세 운영 정보와 다른 직원의 정보는 표시하지 않는다.

---

# 3. 공통 화면 구조

로그인 이후 화면은 공통 레이아웃을 사용한다.

```text
┌──────────────────────────────────────────────────────────────┐
│ Header                                                       │
├───────────────┬──────────────────────────────────────────────┤
│               │                                              │
│ Sidebar       │ Main Content                                 │
│               │                                              │
│               │                                              │
│               │                                              │
└───────────────┴──────────────────────────────────────────────┘
```

---

## 3.1 Header

Header에는 다음 정보를 표시한다.

* 서비스명 또는 로고
* 현재 날짜 및 시간
* 현재 사용자 이름
* 현재 사용자 역할
* 로그아웃 기능

현재 날짜와 시간은 모든 주요 화면에서 확인할 수 있어야 한다.

시간이 중요한 ETA 서비스이므로 사용자가 현재 시간을 쉽게 확인할 수 있도록 한다.

---

## 3.2 Sidebar

Sidebar에서는 주요 화면으로 이동한다.

기본 메뉴:

* 대시보드
* 차량 관제
* 중간 배송 투입 분석

필요한 경우 사용자 역할에 따라 메뉴를 다르게 표시할 수 있다.

### 관리자

* 관리자 대시보드
* 차량 관제
* 중간 배송 투입 분석

### 현장 직원

* 현장 대시보드
* 차량 관제
* 중간 배송 투입 분석

---

## 3.3 페이지 제목 영역

각 화면 상단에는 다음 정보를 표시한다.

* 페이지 제목
* 페이지 설명 또는 현재 조회 범위
* 필요 시 마지막 데이터 갱신 시간

예시:

```text
차량 관제

전체 Hub 및 차량의 실시간 운행 현황
마지막 업데이트: 2026.07.08 05:30
```

---

# 4. 공통 상태 정의

## 4.1 차량 상태

차량 상태는 다음 값을 사용한다.

| 상태 코드        | 표시명  | 의미             |
| ------------ | ---- | -------------- |
| `ARRIVED`    | 도착   | 목적지 Hub에 도착 완료 |
| `IN_TRANSIT` | 운행 중 | 목적지 Hub로 이동 중  |
| `DELAYED`    | 지연   | 예정 기준보다 지연 발생  |

동일한 상태는 모든 페이지에서 동일한 라벨과 색상 규칙을 사용한다.

상태 표시는 텍스트만으로도 구분 가능해야 한다.

색상만으로 상태를 판단하게 하지 않는다.

---

## 4.2 ETA 표시

ETA는 사용자가 즉시 이해할 수 있는 형태로 표시한다.

기본 표시:

```text
06:42 도착 예정
```

필요한 경우 날짜를 포함한다.

```text
07.08 06:42 도착 예정
```

지연이 발생한 경우 ETA와 지연 시간을 함께 표시한다.

```text
ETA 06:42
18분 지연
```

---

## 4.3 지연 시간

지연 시간은 `delayMinutes`를 기준으로 표시한다.

예시:

```text
8분 지연
18분 지연
32분 지연
```

지연 시간이 긴 차량일수록 높은 우선순위로 표시한다.

---

## 4.4 데이터 갱신 시간

ETA 정보에는 예측 결과 갱신 시간을 표시할 수 있다.

예시:

```text
예측 갱신: 05:28
```

오래된 예측 결과를 최신 정보처럼 보이게 하지 않는다.

---

# 5. 로그인 화면

## 5.1 화면 목적

사용자가 시스템에 진입하는 화면이다.

현재 발표용 또는 프로토타입 구현에서는 실제 인증 기능 대신 Mock Login 또는 역할 전환 기능을 사용할 수 있다.

---

## 5.2 화면 구성

```text
┌──────────────────────────────────────┐
│                                      │
│          물류 관제 시스템             │
│                                      │
│  아이디 또는 이메일                   │
│  [                                ]  │
│                                      │
│  비밀번호                             │
│  [                                ]  │
│                                      │
│  □ 로그인 유지                       │
│                                      │
│           [ 로그인 ]                 │
│                                      │
└──────────────────────────────────────┘
```

---

## 5.3 필요 요소

* 아이디 또는 이메일 입력
* 비밀번호 입력
* 로그인 유지
* 로그인 버튼
* 로그인 실패 오류 메시지

---

## 5.4 발표용 역할 전환

실제 인증 기능이 구현되지 않은 경우 다음 방식으로 역할을 전환할 수 있다.

* 관리자로 로그인
* 현장 직원으로 로그인

역할 전환 기능은 발표용 기능임을 코드 구조상 분리하여 실제 인증 로직처럼 보이지 않도록 한다.

---

# 6. 관리자 대시보드

## 6.1 화면 목적

관리자가 전체 물류 상황을 한눈에 파악할 수 있도록 주요 운영 정보를 요약하여 제공한다.

대시보드는 상세 분석 화면이 아니라 다음 질문에 빠르게 답할 수 있어야 한다.

* 현재 차량 운영에 문제가 있는가?
* 어떤 차량이 지연되고 있는가?
* 마지막 차량은 언제 도착하는가?
* 어느 Hub에 문제가 있는가?
* 기다리는 동안 다른 배송 업무를 수행할 수 있는가?

---

## 6.2 전체 화면 구성

```text
┌─────────────────────────────────────────────────────────────┐
│ 물류 관제 대시보드                    2026.07.08 05:30       │
├──────────┬──────────┬──────────┬──────────┬─────────────────┤
│ 전체     │ 도착     │ 운행 중  │ 지연     │ 막차 ETA        │
│ 12       │ 5        │ 5        │ 2        │ 06:42           │
├──────────────────────────────┬──────────────────────────────┤
│ 지연 차량                    │ Hub 운영 현황                │
│                              │                              │
│                              │                              │
├──────────────────────────────┴──────────────────────────────┤
│ 중간 배송 투입 가능 현황                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 6.3 상단 요약 정보

다음 정보를 요약 카드 또는 동일한 수준의 요약 UI로 표시한다.

### 전체 차량

현재 조회 대상 전체 차량 수.

### 도착

목적지 Hub에 도착한 차량 수.

### 운행 중

현재 이동 중인 차량 수.

### 지연

지연 상태인 차량 수.

### 막차 ETA

현재 도착 예정 차량 중 가장 늦은 ETA.

막차 ETA는 단순한 장식 정보가 아니라 운영 판단의 핵심 정보이므로 다른 정보보다 쉽게 확인할 수 있어야 한다.

---

## 6.4 지연 차량 목록

현재 지연 중인 차량을 표시한다.

표시 정보:

* 차량 ID
* 현재 상태
* 도착 Hub
* ETA
* 지연 시간

예시:

```text
TRUCK-07
도착 Hub: HUB-B
ETA: 06:42
18분 지연
```

정렬 기준:

1. 지연 시간이 긴 차량
2. ETA가 임박한 차량

지연 차량이 없는 경우 빈 표만 표시하지 않는다.

예시:

```text
현재 지연 차량이 없습니다.
```

차량을 선택하면 차량 상세 화면으로 이동할 수 있다.

---

## 6.5 Hub 운영 현황

각 Hub의 현재 상황을 요약한다.

표시 정보:

* Hub 이름 또는 ID
* 도착 차량 수
* 운행 중 차량 수
* 지연 차량 수
* 막차 ETA

예시:

```text
HUB-A

도착      4
운행 중   2
지연      1
막차 ETA  06:42
```

문제가 있는 Hub를 쉽게 확인할 수 있어야 한다.

---

## 6.6 중간 배송 투입 가능 현황

현재 대기 인력을 다른 배송 업무에 투입할 수 있는지 요약한다.

표시 정보 예시:

* Hub
* 남은 대기 시간
* 투입 가능 직원 수
* 투입 불가 직원 수

예시:

```text
HUB-A

남은 대기 시간: 72분
투입 가능: 3명
투입 불가: 2명
```

상세 분석이 필요한 경우 중간 배송 투입 분석 화면으로 이동한다.

---

# 7. 현장 직원 대시보드

## 7.1 화면 목적

현장 직원이 자신의 Hub에 도착할 차량 상황을 빠르게 확인한다.

핵심 질문:

* 내 Hub로 오는 차량은 몇 대인가?
* 어떤 차량이 지연되고 있는가?
* 막차는 언제 도착하는가?
* 현재 기다려야 하는가?
* 중간 배송 업무를 수행할 수 있는가?

---

## 7.2 표시 범위

현장 직원에게는 다음 정보만 표시한다.

* 자신의 소속 Hub
* 해당 Hub로 오는 차량
* 해당 차량의 ETA
* 해당 차량의 지연 여부
* 막차 ETA
* 자신의 중간 배송 투입 분석 결과

---

## 7.3 주요 정보

* 도착 완료 차량 수
* 남은 차량 수
* 지연 차량 수
* 막차 ETA
* 남은 대기 시간
* 현재 중간 배송 투입 가능 여부

관리자 화면보다 정보 범위를 좁게 유지한다.

---

# 8. 차량 관제 화면

## 8.1 화면 목적

차량의 현재 위치와 운행 상태를 지도와 목록으로 확인한다.

관리자는 전체 차량을 확인한다.

현장 직원은 자신의 Hub로 오는 차량만 확인한다.

---

## 8.2 전체 화면 구성

```text
┌──────────────────────────────────────────────────────────────┐
│ 차량 관제                                                   │
├───────────────────────────────────────┬──────────────────────┤
│                                       │ 차량 목록            │
│                                       │                      │
│                                       │ TRUCK-01             │
│                지도                   │ TRUCK-02             │
│                                       │ TRUCK-03             │
│                                       │                      │
│                                       │                      │
└───────────────────────────────────────┴──────────────────────┘
```

---

## 8.3 지도 표시 정보

지도에는 다음 정보를 표시한다.

* 차량 현재 위치
* Hub 위치
* 선택된 차량
* 차량 이동 경로

가능한 경우 시간별 GPS 좌표를 사용하여 차량의 이동 경로를 표시한다.

---

## 8.4 관리자 조회 범위

관리자는 다음을 확인할 수 있다.

* 전체 Hub
* 전체 차량
* 전체 차량 위치
* 차량별 도착 Hub
* 차량별 ETA
* 차량별 상태

필요한 경우 Hub 또는 차량 상태를 기준으로 필터링할 수 있다.

---

## 8.5 현장 직원 조회 범위

현장 직원에게는 다음을 표시한다.

* 자신의 Hub
* 자신의 Hub로 오는 차량
* 해당 차량의 현재 위치
* 해당 차량의 ETA
* 해당 차량의 지연 상태

다른 Hub로 이동하는 차량은 기본적으로 표시하지 않는다.

---

## 8.6 차량 목록

차량 목록에는 다음 정보를 표시한다.

* 차량 ID
* 상태
* 도착 Hub
* ETA
* 지연 시간

예시:

```text
TRUCK-01
운행 중
HUB-A
ETA 06:10

TRUCK-07
지연
HUB-B
ETA 06:42
18분 지연
```

---

## 8.7 차량 선택 동작

차량 목록에서 차량을 선택하면:

* 지도에서 해당 차량을 강조한다.
* 선택된 차량의 정보를 확인할 수 있다.

지도에서 차량을 선택하면:

* 차량 목록에서도 동일한 차량을 선택 상태로 표시한다.

지도와 목록의 선택 상태는 항상 동일해야 한다.

---

## 8.8 차량 상세 이동

선택한 차량의 상세 정보를 확인할 수 있는 진입점을 제공한다.

예시:

```text
[ 차량 상세 보기 ]
```

차량 상세 페이지로 이동할 때 `vehicleId`를 기준으로 차량을 식별한다.

---

# 9. 차량 상세 화면

## 9.1 화면 목적

특정 차량의 현재 운행 상태, 위치, 이동 경로 및 ETA 정보를 상세하게 확인한다.

---

## 9.2 화면 구성

```text
┌──────────────────────────────────────────────────────────────┐
│ ← 차량 목록              TRUCK-01                            │
├───────────────────────────────────────┬──────────────────────┤
│                                       │ 차량 정보            │
│                                       │                      │
│                지도                   │ 상태: 지연           │
│                                       │ ETA: 06:42           │
│                                       │ 지연: 18분           │
│                                       │                      │
└───────────────────────────────────────┴──────────────────────┘
```

---

## 9.3 기본 정보

다음 정보를 표시한다.

* 차량 ID
* 차량 상태
* 출발 Hub
* 도착 Hub

---

## 9.4 ETA 정보

다음 정보를 표시한다.

* 예상 도착 시간
* 지연 시간
* 예측 갱신 시간

가능한 경우 다음 정보를 추가한다.

* 예측 신뢰도
* 지연 사유

예시:

```text
예상 도착 시간
06:42

현재 지연
18분

예측 갱신
05:28

예측 신뢰도
87%
```

---

## 9.5 위치 및 경로 정보

지도에 다음 정보를 표시한다.

* 현재 차량 위치
* 출발 위치
* 도착 Hub
* 지금까지 이동한 경로
* 남은 이동 경로

가능한 경우 다음 정보도 표시한다.

* 남은 거리
* 예상 남은 이동 시간

---

## 9.6 데이터 갱신

차량 상세 화면의 위치와 ETA 데이터는 갱신될 수 있다.

갱신 시 화면 전체를 불필요하게 다시 로드하지 않는다.

사용자가 확인 중인 차량 선택 상태와 화면 위치는 가능한 한 유지한다.

# 10. 중간 배송 투입 분석 화면

## 10.1 화면 목적

지연 차량 도착까지 남은 시간 동안 일부 배송 업무를 먼저 수행하는 것이 효율적인지 판단한다.

이 화면은 단순히 남은 시간을 보여주는 것이 아니라 실제 운영 결정을 지원해야 한다.

---

## 10.2 관리자 핵심 질문

관리자는 다음 질문에 답할 수 있어야 한다.

* 현재 대기 인력을 다른 배송 업무에 투입할 수 있는가?
* 어떤 Hub에서 대기 시간이 발생하고 있는가?
* 어떤 직원이 투입 가능한가?
* 투입한 직원이 막차 도착 전에 복귀할 수 있는가?

---

## 10.3 현장 직원 핵심 질문

현장 직원은 다음 질문에 답할 수 있어야 한다.

* 지금 대기하는 것이 유리한가?
* 중간 배송을 다녀오는 것이 유리한가?
* 중간 배송 후 막차 도착 전에 복귀할 수 있는가?

---

## 10.4 분석 기준 정보

분석에는 다음 정보를 사용한다.

* 현재 시간
* 막차 ETA
* 남은 대기 시간
* 예상 배송 작업 시간
* 예상 이동 시간
* 예상 복귀 시간
* 안전 여유 시간

---

## 10.5 분석 계산 개념

기본 판단 구조:

```text
남은 대기 시간
=
막차 ETA - 현재 시간
```

```text
필요 작업 시간
=
예상 배송 작업 시간 + 안전 여유 시간
```

기본 판단 예시:

```text
남은 대기 시간 >= 필요 작업 시간
→ 투입 가능
```

```text
남은 대기 시간 < 필요 작업 시간
→ 투입 불가
```

최종 판단 로직은 서버 또는 분석 결과 데이터를 기준으로 한다.

프론트엔드에서 임의로 업무 판단 규칙을 추가하지 않는다.

---

## 10.6 현장 직원 화면 예시

│ 중간 배송 투입 분석                          │

## 10.7 관리자 화면

관리자는 Hub별 또는 직원별 분석 결과를 확인한다.

표시 정보 예시:

* Hub
* 직원
* 막차 ETA
* 남은 대기 시간
* 예상 작업 소요 시간
* 예상 복귀 시간
* 안전 여유 시간
* 투입 가능 여부

예시:

| 직원     | Hub   | 남은 대기 | 예상 작업 | 예상 복귀 | 결과    |
| ------ | ----- | ----: | ----: | ----- | ----- |
| EMP-01 | HUB-A |   72분 |   38분 | 06:23 | 투입 가능 |
| EMP-02 | HUB-A |   72분 |   65분 | 06:50 | 투입 불가 |

## 10.8 최종 결과 표시

최종 결과는 사용자가 즉시 이해할 수 있도록 명확하게 표시한다.

### 투입 가능

```text
투입 가능

막차 도착 전에 복귀할 수 있습니다.
예상 여유 시간: 19분
```

### 투입 불가

```text
투입 불가

예상 복귀 시간이 막차 ETA보다 늦습니다.
현재 위치에서 대기하는 것을 권장합니다.
```

결과는 색상만으로 전달하지 않는다.

# 11. 공통 상호작용 규칙

## 11.1 로딩 상태

데이터를 불러오는 동안 빈 화면을 표시하지 않는다.

예시:

```text
차량 정보를 불러오는 중입니다.
```

필요한 경우 Skeleton UI를 사용할 수 있다.

---

## 11.2 오류 상태

API 요청 실패 시 사용자에게 오류 상태를 표시한다.

예시:

```text
차량 정보를 불러오지 못했습니다.

[ 다시 시도 ]
```

콘솔 오류만 발생시키고 화면을 비워두지 않는다.

---

## 11.3 빈 데이터 상태

데이터가 없는 경우 빈 표를 표시하지 않는다.

예시:

```text
현재 지연 차량이 없습니다.
```

```text
현재 조회 가능한 차량이 없습니다.
```

---

## 11.4 날짜 및 시간

서비스 내 시간 표기는 일관되게 유지한다.

기본 형식:

```text
HH:mm
```

날짜가 필요한 경우:

```text
YYYY.MM.DD HH:mm
```

---

## 11.5 숫자 및 시간 단위

단위를 생략하지 않는다.

예시:

```text
18분
32km
87%
```

# 12. 공통 UI 설계 원칙

이 서비스는 홍보용 랜딩 페이지가 아니라 운영용 대시보드이다.

다음 원칙을 따른다.

* 정보 확인 속도를 우선한다.
* 중요 정보가 화면 상단에 위치한다.
* 과도한 장식 요소를 사용하지 않는다.
* 지나치게 큰 제목이나 Hero Section을 사용하지 않는다.
* 불필요한 Gradient 사용을 피한다.
* 동일한 기능은 동일한 형태로 표시한다.
* 상태 색상과 라벨은 모든 화면에서 일관되게 유지한다.
* 카드가 필요하지 않은 정보까지 모두 카드 형태로 만들지 않는다.
* 데이터 밀도와 가독성의 균형을 유지한다.
* 발표용 화면에서도 실제 운영 대시보드처럼 보이도록 구성한다.

1280px

# 14. Mock Data 사용 규칙

백엔드 API가 준비되지 않은 경우 Mock Data를 사용할 수 있다.

Mock Data는 UI 컴포넌트 내부에 직접 작성하지 않는다.

예시 구조:

```text
src/
├─ mocks/
│  ├─ vehicles.ts
│  ├─ hubs.ts
│  ├─ employees.ts
│  └─ dashboard.ts
```

실제 API 연결 시 Mock Data를 쉽게 교체할 수 있어야 한다.

Mock Data의 필드 구조는 실제 API 응답 구조와 최대한 동일하게 유지한다.

---

# 15. 데이터 사용 원칙

프론트엔드는 AWS 내부 서비스를 직접 호출하지 않는다.

다음 서비스에 직접 요청하지 않는다.

* Amazon SageMaker
* AWS Lambda
* Amazon Kinesis Data Streams
* Amazon S3

프론트엔드는 API Gateway를 통해 필요한 데이터를 조회한다.

기본 구조:

```text
Frontend
   ↓
API Gateway
   ↓
Lambda
   ↓
AWS Services
```

ETA 예측 결과 또한 프론트엔드에서 SageMaker를 직접 호출하지 않고 API 응답으로 전달받는다.

# 16. 구현 시 금지 사항

다음 행동을 하지 않는다.

* 문서에 없는 주요 페이지를 임의로 추가
* 동일한 데이터를 페이지마다 다른 필드명으로 사용
* `vehicleId`와 `truckId`를 혼용
* 임의의 사용자 역할 추가
* 관리자 데이터를 현장 직원 화면에 노출
* Mock Data를 여러 컴포넌트에 중복 작성
* UI 컴포넌트 내부에서 AWS 서비스를 직접 호출
* API가 없는 기능을 실제 동작하는 것처럼 구현
* 페이지마다 차량 상태 이름과 색상을 다르게 사용

프론트엔드는 다음 순서로 구현한다.

1. 프로젝트 공통 레이아웃
2. 라우팅
3. 공통 타입 정의
4. Mock Data 구조
